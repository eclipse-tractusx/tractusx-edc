    Deployment overview¶

    This section takes you from "I have nothing" to "my connector runs in production". Start with Deploy in five minutes below, then plan the real deployment with the rest of this page.

    Deploy in five minutes¶

    Pick the variant that matches what you want to do. All four use the published Helm charts and Docker Hub images, so there is nothing to build. You need Docker, kind (or any other Kubernetes cluster), kubectl and Helm 3.

    One pod, everything in memory: the fastest way to see the Management API. For laptops only, it loses all data on restart.

    # 1. A local Kubernetes cluster (skip if you already have one)
kind create cluster --name tractusx-edc

# 2. The Tractus-X Helm repository
helm repo add tractusx-edc https://eclipse-tractusx.github.io/charts/dev
helm repo update

# 3. Minimal values: dummy identity settings and a local API key
cat > edc-try.yaml <<'EOF'
fullnameOverride: tx-edc
participant:
  id: "did:web:changeme"
  bpnl: "BPNL000000000001"
  contextId: "try-participant-context"
dcp:
  sts:
    div:
      url: "https://div.example.org"
    oauth:
      token_url: "https://div.example.org/oauth/token"
      client:
        id: "try-client-id"
        secret_alias: "try-client-secret"
runtime:
  endpoints:
    management:
      authKey: password
  securityContext:
    readOnlyRootFilesystem: false
  bdrs:
    server:
      url: "https://bdrs.example.org"
  token:
    signer:
      privatekey_alias: "key-1"
    verifier:
      publickey_alias: "key-1"
EOF

# 4. Install, then run the chart's own tests
helm install tx-edc tractusx-edc/tractusx-connector-memory -f edc-try.yaml --wait --timeout 5m
helm test tx-edc

    Talk to the Management API:

    kubectl port-forward deployment/tx-edc 8081:8081 &

curl -s -X POST http://localhost:8081/management/v3/assets/request \
  -H "X-Api-Key: password" -H "Content-Type: application/json" \
  -d '{"@context": {"@vocab": "https://w3id.org/edc/v0.0.1/ns/"}, "@type": "QuerySpec"}'

    [] means the connector is up and you are authenticated. Clean up with kind delete cluster --name tractusx-edc.

    The production chart: a control plane and a data plane, with a PostgreSQL and a dev-mode Vault installed next to them. Close to a real deployment, still with dummy identity settings.

    kind create cluster --name tractusx-edc
helm repo add tractusx-edc https://eclipse-tractusx.github.io/charts/dev
helm repo update

cat > edc-local.yaml <<'EOF'
fullnameOverride: tx-edc
participant:
  id: "did:web:changeme"
  bpnl: "BPNL000000000001"
  contextId: "local-participant-context"
dcp:
  sts:
    div:
      url: "https://div.example.org"
    oauth:
      token_url: "https://div.example.org/oauth/token"
      client:
        id: "local-client-id"
        secret_alias: "client-secret"
controlplane:
  endpoints:
    management:
      authKey: password
  bdrs:
    server:
      url: "https://bdrs.example.org"
dataplane:
  token:
    signer:
      privatekey_alias: "key-1"
    verifier:
      publickey_alias: "key-1"
# install.postgresql and install.vault default to true: seed the dev Vault
vault:
  hashicorp:
    url: http://{{ .Release.Name }}-vault:8200
    token: root
  server:
    postStart:
      - sh
      - -c
      - |-
        {
        sleep 5
        /bin/vault kv put secret/client-secret content=kEmH7QRPWhKfy8f+x0pFMw==
        /bin/vault kv put secret/aes-keys content=YWVzX2VuY2tleV90ZXN0Cg==
        }
EOF

helm install tx-edc tractusx-edc/tractusx-connector -f edc-local.yaml --wait --timeout 10m
kubectl rollout status deployment tx-edc-controlplane
kubectl rollout status deployment tx-edc-dataplane
helm test tx-edc

    The Management API is on the control plane: kubectl port-forward deployment/tx-edc-controlplane 8081:8081, then the same curl as in the first tab.

    A real deployment uses your PostgreSQL, Vault, identity (DID, credential service, BDRS) and hostnames. Write them into a values file first: a minimal production values file is the starting point, and the checklist below lists what you need.

    helm repo add tractusx-edc https://eclipse-tractusx.github.io/charts/dev
helm repo update
helm search repo tractusx-edc/tractusx-connector -l     # pick a released version

helm install my-connector tractusx-edc/tractusx-connector \
  --version <chart-version> \
  --namespace edc --create-namespace \
  -f my-values.yaml --wait --timeout 10m

helm test my-connector --namespace edc

    Then work through the production checklist before you let partners in.

    The Tractus-X Umbrella deploys a complete dataspace on one cluster: a provider and a consumer Tractus-X EDC, each with its own Tractus-X Identity Hub (DCP wallet with STS), an IssuerService that issues their credentials, and the BDRS. Since Umbrella release 25.12 this is its default setup.

    git clone https://github.com/eclipse-tractusx/tractus-x-umbrella.git
cd tractus-x-umbrella/charts/umbrella
helm dependency update
helm install -f values-adopter-decentralized-identityhub.yaml umbrella . \
  --namespace umbrella --create-namespace

    Prepare the cluster (ingress, host names) with the Umbrella guide for Linux, macOS or Windows, then follow Data exchange with the Identity Hub for the participant DIDs and BPNs and a Bruno collection for the first exchange.

    The first two variants cannot join a dataspace

    Their DID, credential service and BDRS are placeholders. The connector starts, its APIs answer and the Helm tests pass, but it cannot negotiate with a real partner. For a complete local dataspace with two connectors and identity services, use the Umbrella tab above or the MXD tutorial. To run the charts with images you built yourself, follow the local quick start, which is the CI deployment test.

    What you deploy¶

    Tractus-X EDC ships as container images and Helm charts. Pick the runtime that matches your goal:

    Image (tractusx/… on Docker Hub) What it is Use it for
    edc-controlplane-postgresql-hashicorp-vault Control plane with PostgreSQL stores and HashiCorp Vault Production
    edc-dataplane-hashicorp-vault Data plane with PostgreSQL and HashiCorp Vault Production
    edc-runtime-memory Control plane and data plane in one JVM, in-memory stores and vault Development and tests only
    Helm chart Deploys Use it for
    tractusx-connector A control plane and a data plane Deployment, optionally PostgreSQL and Vault as subcharts Production
    tractusx-connector-memory One Deployment running edc-runtime-memory Development and tests only

    The in-memory runtime loses everything on restart

    edc-runtime-memory keeps assets, contracts and secrets in memory, in plain text. It cannot run more than one replica. Never use it for real data.

    Images are multi-architecture (linux/amd64, linux/arm64) and run as a non-root user. Charts are published to the Tractus-X Helm repository https://eclipse-tractusx.github.io/charts/dev.

    The production topology¶

    flowchart LR
  subgraph Internet
    partner[Partner connectors]
    consumerApp[Partner data consumers]
  end
  subgraph Your cluster
    direction LR
    ing[Ingress / Gateway<br/>TLS termination]
    cp[Control plane<br/>edc-controlplane-postgresql-hashicorp-vault]
    dp[Data plane<br/>edc-dataplane-hashicorp-vault]
    ing -- "DSP /api/v1/dsp" --> cp
    ing -- "public /api/public" --> dp
    cp -- "control API" --> dp
    dp -- "registers via /v1/dataplanes" --> cp
  end
  subgraph Your platform
    pg[(PostgreSQL)]
    vault[(HashiCorp Vault)]
    apps[Your applications]
  end
  subgraph Dataspace services
    wallet[Credential service / DIV]
    bdrs[BDRS]
    issuer[Credential issuer]
  end
  partner --> ing
  consumerApp --> ing
  apps -- "Management API (internal only)" --> cp
  cp --> pg
  dp --> pg
  cp --> vault
  dp --> vault
  cp --> wallet
  cp --> bdrs
  wallet -.-> issuer

    What this means for you:

    • Two public endpoints. Only the control plane's protocol (DSP) endpoint and the data plane's public endpoint face the internet.
    • Everything else stays internal. The Management API, the control API and the metrics port must never be reachable from outside.
    • Both planes need PostgreSQL and Vault. The data plane also has SQL stores and runs the database migrations.
    • Identity comes from outside. You need a DID, a DCP wallet with a Secure Token Service (STS) and the BDRS of your dataspace. Wallets in use with Tractus-X EDC are the open-source Tractus-X Identity Hub and SAP's managed Decentralized Identity Verification (DIV); any wallet that implements DCP works. See Identity and trust.

    Prerequisites checklist¶

    Before you install the production chart, have these ready:

    • A Kubernetes cluster and Helm 3.
    • A PostgreSQL database (with a dedicated user) reachable from the cluster.
    • A HashiCorp Vault with a KV secrets engine and a token for the connector.
    • Your DID (participant.id) and BPNL (participant.bpnl).
    • A fresh, stable participant context id (a UUID). It must never change later.
    • OAuth client credentials for your credential service (STS/DIV) and the client secret stored in Vault.
    • The BDRS URL of your dataspace.
    • A key pair in Vault for signing and verifying data plane tokens.
    • Two hostnames with TLS certificates: one for the control plane protocol endpoint, one for the data plane public endpoint.
