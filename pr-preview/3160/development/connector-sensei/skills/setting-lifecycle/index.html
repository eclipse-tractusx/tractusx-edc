    Setting lifecycle¶

    Connector Sensei skill

    When it is used: Add, rename, deprecate, remove or look up a Tractus-X EDC configuration setting end to end, covering the @Setting declaration, env var, Helm template, values.yaml, helm-docs README, extension README, migration guide and tests. Use for "what is the env var / Helm value for X", "add a config option", "rename this setting", "why is my setting ignored", or any change touching charts/*/values.yaml.

    Scripts: setting-trace.sh · Source: .claude/skills/setting-lifecycle/SKILL.md

    A connector setting usually lives in up to seven places. Most migration-guide content in docs/migration/ is old→new tables for settings and Helm values, so missing one place is the most common review comment and operator-facing bug.

    # Place Example
    1 @Setting declaration (Tractus-X or upstream) BdrsClientExtension.java: @Setting(key = BDRS_SERVER_URL_PROPERTY, …)
    2 Env var name tx.edc.iam.dcp.bdrs.server.url → TX_EDC_IAM_DCP_BDRS_SERVER_URL (upper-case, . and - → _)
    3 Helm template that sets it charts/tractusx-connector/templates/deployment-controlplane.yaml (and -dataplane, plus tractusx-connector-memory/templates/deployment-runtime.yaml)
    4 Helm value charts/*/values.yaml, with a # -- comment that helm-docs renders
    5 Chart README charts/*/README.md, generated by helm-docs from README.md.gotmpl and verified in CI
    6 Extension README edc-extensions/<ext>/README.md ## Configuration table
    7 Migration guide docs/migration/<date>-Version_<x>_<y>.md for renames, removals, default changes

.claude/skills/setting-lifecycle/scripts/setting-trace.sh EDC_PARTICIPANT_ID

    It resolves key ↔ env var ↔ Helm path, shows the declaration (Tractus-X and upstream at the pinned version), the template lines, the values.yaml entries in every chart, the docs, the migration history and the tests. It ends with a touchpoint checklist.

    Adding a setting¶

    1. Declare it on the extension that consumes it: 
      static final String FOO_TIMEOUT = "tx.edc.foo.timeout";
@Setting(key = FOO_TIMEOUT, description = "Timeout in seconds for …", defaultValue = "30")
private int timeout;
    2. Prefixes: tx.edc.* for Tractus-X features, tractusx.edc.* for participant identity, and edc.* only when you configure an upstream setting.
    3. Use required = false or a defaultValue unless the runtime cannot start without it.
    4. For grouped settings consider a @Settings record (see upstream edc-src.sh grep '@Settings').
    5. Expose it in the chart only if operators need it. Add the env var under the right plane's env: block, guarded when optional: 
      {{- if .Values.controlplane.foo.timeout }}
- name: "TX_EDC_FOO_TIMEOUT"
  value: {{ .Values.controlplane.foo.timeout | quote }}
{{- end }}
      Add the value with a helm-docs comment in each chart (tractusx-connector uses controlplane.* / dataplane.*; tractusx-connector-memory uses runtime.*): 
      foo:
  # -- Timeout in seconds for …
  timeout: 30
    6. Regenerate the chart READMEs: docker run --rm -v "$PWD/charts:/helm-docs" jnorwood/helm-docs helm-docs (the same command as CI's verify-helm-docs).
    7. Document it in the extension README configuration table.
    8. Test it: an extension test with ConfigFactory.fromMap(Map.of(FOO_TIMEOUT, "5")), and a Helm template test in charts/*/templates/tests when the template logic is non-trivial.

    Renaming a setting (deprecate, then remove)¶

    Never rename in one step. Tractus-X deprecates first and removes in a later release; for example the 0.13 guide removed settings deprecated since 0.8.

    1. Keep the old key working: read the new key and fall back to the old one with a warning: 
      @Deprecated(since = "0.14.0")
static final String OLD_KEY = "tx.edc.old.key";
static final String NEW_KEY = "tx.edc.new.key";
…
var value = config.getString(NEW_KEY, null);
if (value == null && config.hasKey(OLD_KEY)) {
    monitor.warning("Setting '%s' is deprecated, use '%s' instead".formatted(OLD_KEY, NEW_KEY));
    value = config.getString(OLD_KEY);
}
    2. In the chart, emit the new env var and accept the old value as a fallback: {{ .Values.new.path | default .Values.old.path }}. Keep the old value commented as deprecated in values.yaml.
    3. Add a migration-guide row in the established format: | Old value | New value | New environment variable | (or the Old Helm value | New Helm value table).
    4. Removal later: delete the fallback and the old Helm value, and note the removal in that release's guide.

    Removing or changing a default¶

    These are breaking for operators. Add a migration-guide entry, run .claude/skills/breaking-change-guard/scripts/bc-scan.sh, and mention it in the PR description.

    Debugging "my setting is ignored"¶

    1. Trace it and confirm the env var name is spelled exactly as derived from the key.
    2. Check that the setting is consumed by the right runtime (control plane vs data plane) and that the extension is in that runtime's build.gradle.kts.
    3. Check whether upstream also declares the key (the trace shows it); an upstream @Setting may win or differ in default.
    4. Check where the value is read. Since EDC 0.15 some services read configuration through the participant context (ParticipantContextConfig, single-participant store in participant-context-connector-classic-core) rather than context.getConfig(). Use edc-src.sh grep on the key to see which path applies.
