# Migration Guide `0.13.x -> 0.14.x`

This document outlines the necessary changes for migrating your tractusx-edc installation from versions 0.13.x to 0.14.x.
It also outlines some points that adopters and operators should pay close attention to when migrating from one version
to another.

This document is not a comprehensive feature list.

## 1. Upstream EDC 0.18.2

Tractus-X EDC is now based on upstream Eclipse EDC `0.18.2`. The cloud extensions `org.eclipse.edc.aws:*` and
`org.eclipse.edc.azure:*` are used in version `0.18.0`, as no `0.18.2` release exists for them.

Upstream added the column `data_address_owner` to `edc_transfer_process`. It is created by the migration
`V1_10_0__Add_DataAddressOwnerColumn.sql`, which runs automatically on start-up when the Tractus-X migrations are
enabled. The column decides how a suspended transfer process is resumed. The migration sets it for existing
provider-side `*-PULL` transfer processes, the only ones for which upstream sets it with the legacy data plane
signaling (see below), so that transfers suspended before the upgrade can still be resumed by the provider.

### 1.1 Data plane signaling

Since `0.18.0` the upstream control plane BOM ships the new Data Plane Signaling implementation
(`data-plane-signaling`) instead of the legacy one (`transfer-data-plane-signaling`). The two are not compatible on the
wire, and the Tractus-X data plane, like the upstream data plane `0.18.x`, still speaks the legacy protocol.

The Tractus-X control plane therefore excludes the new `data-plane-signaling` modules and keeps the legacy signaling.
It is provided by the new extension [`legacy-data-plane-signaling`](../../edc-extensions/legacy-data-plane-signaling/README.md),
a backport of the deprecated upstream module `transfer-data-plane-signaling` that replaces it. The backport fixes the
resumption of suspended transfer processes (`POST /v3/transferprocesses/{id}/resume`), which the upstream legacy module
breaks in EDC `0.18`: the provider issued an EDR without audience, and the consumer of a PULL transfer terminated the
transfer process instead of resuming it. In addition, the consumer now stores the new EDR issued on resumption, where
upstream EDC `0.18` hands the EDR of the first start to the EDR store again.

Nothing changes for operators: control plane and data plane `0.14.x` work together, and data plane registration and
configuration (e.g. `edc.dataplane.client.selector.strategy`) stay as they are.

Upstream announced that the legacy module will be removed in a future release. Tractus-X will migrate both control
plane and data plane to the new signaling protocol in a coordinated release.

### 1.2 HashiCorp Vault authentication settings

Upstream EDC removed the OAuth2 client credentials authentication of the HashiCorp Vault extension and replaced it with
token exchange and JWT authentication:

| Removed setting                     | Replacement                                         |
|-------------------------------------|-----------------------------------------------------|
| `edc.vault.hashicorp.clientid`      | `edc.vault.hashicorp.auth.tokenexchange.*`          |
| `edc.vault.hashicorp.clientsecret`  | `edc.vault.hashicorp.auth.tokenexchange.*`          |
| `edc.vault.hashicorp.tokenurl`      | `edc.vault.hashicorp.auth.tokenexchange.url`        |
|                                     | `edc.vault.hashicorp.auth.jwt.role` (JWT auth)      |

The Tractus-X Helm charts never exposed the removed settings, so only installations that set them through custom
environment variables are affected. Token authentication (`edc.vault.hashicorp.token`) is unchanged.

### 1.3 Changes for adopters building custom runtimes or extensions

- Custom control plane runtimes built on the upstream BOMs must exclude `org.eclipse.edc:transfer-data-plane-signaling`
  and the new `data-plane-signaling` modules, and add `org.eclipse.tractusx.edc:legacy-data-plane-signaling` instead,
  see its [README](../../edc-extensions/legacy-data-plane-signaling/README.md). The extension refuses to start when the
  upstream module is on the classpath as well, since both provide a `DataFlowController`.
- The module `edc-extensions:dsp:dsp-http-dispatcher-08` has been removed. Upstream EDC `0.18` replaced the
  per-protocol `RemoteMessageDispatcherRegistry` with a single `ProtocolRemoteMessageDispatcher` that serves all
  registered dataspace profiles, DSP 0.8 included, so the module had nothing left to register. Remove it from custom
  runtimes.
- The DSP 0.8 JSON-LD scope `Dsp08Constants.DSP_SCOPE_V_08` changed from `DSP:v0.8` to `DSP:dataspace-protocol-http`,
  as upstream EDC now keys the DSP JSON-LD scope by dataspace profile name instead of protocol version (`DSP_SCOPE_V_2025_1`
  changed the same way). Extensions that register JSON-LD namespaces or contexts for DSP 0.8 must use the constant
  rather than a literal value.
- `callback-spi`: the upstream `CallbackEventRemoteMessage` was removed. `InProcessCallback#invoke` and
  `InProcessCallbackRegistry#handleMessage` now take an `InProcessCallbackMessage`, which provides the same
  `getEventEnvelope()` plus `getCallbackAddress()`. `local://` callbacks are now handled by a `CallbackClient`
  provided by the `edr-callback` extension, which delegates every other callback address to the upstream HTTP
  callback client. As before, a failing in-process callback is logged and does not roll back the transaction that
  emitted the event.
